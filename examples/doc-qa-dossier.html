The problemEl problema

A support team has 4,000 internal help pages. People ask questions in their own words, and the answers exist somewhere in those pages, but nobody can find them. A language model on its own cannot help: it has never read those pages, and pasting all 4,000 into every question is far too much text for it to accept.

Un equipo de soporte tiene 4.000 páginas de ayuda internas. La gente pregunta con sus propias palabras y las respuestas están en algún lado de esas páginas, pero nadie las encuentra. Un modelo de lenguaje solo no alcanza: nunca leyó esas páginas, y pegarle las 4.000 en cada pregunta es muchísimo más texto del que puede aceptar.

What was builtQué se construyó

A small web service with two jobs. Ingestion runs once: it reads every help page, cuts each one into overlapping passages, turns every passage into a list of numbers that captures its meaning, and files them in a database that can find similar lists quickly.

Answering runs on every question: it converts the question into the same kind of number list, asks the database for the five closest passages, pastes only those five into a prompt, and asks the model to answer using nothing but that text.

Un servicio web chico con dos trabajos. La ingesta corre una sola vez: lee cada página de ayuda, la corta en pasajes que se superponen, convierte cada pasaje en una lista de números que captura su significado y los archiva en una base de datos que encuentra listas parecidas rápido.

La respuesta corre en cada pregunta: convierte la pregunta en el mismo tipo de lista de números, le pide a la base los cinco pasajes más cercanos, pega solamente esos cinco en un prompt y le pide al modelo que responda usando nada más que ese texto.

The reference explanationLa explicación de referencia

A help page can be six screens long and cover eight unrelated things: how to log in, how to reset a password, what the error codes mean, and so on. If you file the whole page as one item, then its one summary has to stand for all eight topics at once — and a summary of eight things is a good match for none of them.

So before filing, each page is cut into pieces of roughly a paragraph or two. Each piece is about one thing, so its summary is sharp. The cuts overlap a little, because the sentence that actually answers a question has a habit of landing exactly where you made the cut, and the overlap guarantees at least one piece still contains it whole.

Una página de ayuda puede tener seis pantallas de largo y cubrir ocho cosas que no tienen nada que ver: cómo entrar, cómo resetear una contraseña, qué significan los códigos de error, etcétera. Si archivás la página entera como un solo ítem, su único resumen tiene que representar los ocho temas a la vez — y un resumen de ocho cosas no coincide bien con ninguna.

Así que antes de archivar, cada página se corta en pedazos de más o menos uno o dos párrafos. Cada pedazo habla de una sola cosa, entonces su resumen es filoso. Los cortes se superponen un poco, porque la oración que realmente contesta la pregunta tiene la costumbre de caer justo donde hiciste el corte, y la superposición garantiza que al menos un pedazo la siga teniendo entera.

src/qa_reference.py
"""Reference implementation. Read this only after your own version passes."""
import math

FLOOR = 0.72
TOP_K = 5
_STORE = []  # {url, text, vec}


def reset():
    _STORE.clear()


def count():
    return len(_STORE)


def split(text, size=800, overlap=150):
    if size <= overlap:
        raise ValueError("size must exceed overlap")
    step = size - overlap
    pieces, i = [], 0
    while i < len(text):
        pieces.append(text[i:i + size])
        if i + size >= len(text):
            break
        i += step
    return pieces


def score(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    na = math.sqrt(sum(x * x for x in a))
    nb = math.sqrt(sum(y * y for y in b))
    if na == 0 or nb == 0:
        return 0.0
    return dot / (na * nb)


def ingest(docs):
    for doc in docs:
        # Delete-then-insert is what keeps re-ingestion idempotent.
        _STORE[:] = [r for r in _STORE if r["url"] != doc["url"]]
        for piece in split(doc["text"]):
            _STORE.append({"url": doc["url"], "text": piece, "vec": embed(piece)})


def search(vec, k=TOP_K):
    scored = [(score(vec, r["vec"]), r) for r in _STORE]
    scored.sort(key=lambda p: p[0], reverse=True)
    return scored[:k]


def ask(question):
    hits = [(s, r) for s, r in search(embed(question)) if s >= FLOOR]
    if not hits:
        # Return before the prompt is built: refusing must cost nothing.
        return {"answer": "I don't know based on the documents I have.", "sources": []}
    passages = "\n\n---\n\n".join(r["text"] for _, r in hits)
    prompt = (
        "Answer the question using ONLY the passages below. "
        "If they do not contain the answer, say so plainly.\n\n"
        f"PASSAGES:\n{passages}\n\nQUESTION: {question}"
    )
    sources, seen = [], set()
    for _, r in hits:
        if r["url"] not in seen:
            seen.add(r["url"])
            sources.append(r["url"])
    return {"answer": generate(prompt), "sources": sources}

The system at staff levelEl sistema a nivel staff

This is a two-stage system where the interesting engineering is entirely in stage one. Generation quality is effectively a constant you bought from a vendor; retrieval quality is the variable you control, and it sets the ceiling on everything the user sees. That single observation determines where effort belongs: passage size, splitting strategy, and the refusal floor are the levers, while prompt wording is a rounding error.

The design's real strength is that it fails closed. The floor check happens before the generation call, so an unanswerable question costs nothing and produces a refusal rather than a fabrication. Its real weakness is that the whole quality story rests on one hand-tuned constant that is silently coupled to the embedding model version and is not monitored anywhere.

If you reviewed this, the highest-value comment is not about the code — it is that the refusal rate must become a monitored metric with an alert, and that below-floor queries must be logged. Without those two, this system can decay into uselessness while every infrastructure dashboard stays green.

How would you tell whether a wrong answer was a retrieval failure or a generation failure?

¿Cómo distinguirías si una respuesta equivocada fue una falla de búsqueda o una de generación?

Read the cited passages. If they contain the correct answer, generation misread them and the fix is in the prompt or the model. If they do not, retrieval failed and the fix is in splitting, the floor, or adding keyword search. This is precisely why sources are returned, and why a version that returned only prose would be nearly impossible to improve.

Leer los pasajes citados. Si contienen la respuesta correcta, la generación los leyó mal y el arreglo está en el prompt o el modelo. Si no, falló la búsqueda y el arreglo está en el corte, el piso o agregar búsqueda por palabra clave. Por esto exactamente se devuelven las fuentes, y por eso una versión que devolviera solo prosa sería casi imposible de mejorar.

What is the first thing you would add, and defend the choice against "just use a better model".

¿Qué es lo primero que agregarías, y defendé la elección contra "usá un modelo mejor"?

Logging of below-floor queries. A better generation model cannot answer from passages it never received, so it cannot fix a retrieval miss — and until you can see which questions are missing, every other improvement is a guess. It is also nearly free, which makes it the highest ratio of information gained to work done in the whole system.

Loguear las consultas que caen bajo el piso. Un modelo de generación mejor no puede contestar desde pasajes que nunca recibió, así que no puede arreglar una falla de búsqueda — y hasta que no puedas ver qué preguntas se están perdiendo, cualquier otra mejora es una adivinanza. Además es casi gratis, lo que lo vuelve la mejor relación entre información ganada y trabajo hecho de todo el sistema.
